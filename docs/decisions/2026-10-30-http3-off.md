# Dropped connections on the cloud site: retry, time out, HTTP/3 off (2026-10-30)

## What Leon saw
- 新建节目: the first 确认 said "Failed to fetch", the second worked.
- 文字稿 → 删除这段 / 只静音: hung; every edit button stayed grey until a refresh; after the refresh the word was
  gone (the server had made the cut, its answer never reached the page). The refresh itself took 20-60 s.
- 剪辑时间线: past a point (4:45) both lanes stayed empty while playing, until he switched pages.
- Console: `net::ERR_QUIC_PROTOCOL_ERROR`.

## Cause
One cause for all four: the browser's HTTP/3 (QUIC) connection to Cloudflare broke while the page sat open.
A request sent on it either failed at once ("Failed to fetch"; the browser then opens a new connection, so the
second click works) or got no answer at all, and the page waited forever (no timeout): the cut's button stayed
busy, the waveform tiles stayed "loading" (fetched once, never asked again), and the refresh waited for the
browser to give up on the dead connection. The server itself answers these in milliseconds (measured on a
51-minute, two-track, 300-edit episode: cut 34 ms, a waveform tile 40 ms, the episode 3 ms).

## Decision
- The page: a request that got no answer at all (`TypeError`) is sent once more by itself (`web/src/api.ts`).
  Requests the server answers at once (manual cut, waveform tiles, transcript stretches) give up after 20 s
  (`lost`); a timed-out request is never resent (the server may have done it). After any failed edit action
  the episode is loaded again, so what the server has is on screen. Waveform / transcript chunks that failed are
  asked for again (up to 4 times); after a cut the old waveform stays until the new tiles arrive.
- Cloudflare: HTTP/3 off for the zone (Provision mode `http3-off`; `http3-check` only shows it). Browsers speak
  HTTP/2, which recovers from a dropped connection by itself. Turn it back on from the Cloudflare dashboard
  (Speed → Optimization → Protocol Optimization → HTTP/3) if ever needed.
