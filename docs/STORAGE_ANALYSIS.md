# 存储方案分析：JSON 还是数据库（2026-10-17）

**一句话结论：现在不用换数据库，几十上百集也撑得住；真正该马上补的是「自动备份」，和「首页别一次把所有剧集读进内存」。等到要跨上百集做学习/搜索，或者真的和 Pei 同时编辑同一集时，再换 SQLite，届时改动集中在存储层，Claude 实际执行约半天。**

依据：main `21bed2e` 的代码，加上只读查看你电脑上 `C:\Projects\LACUNA_Workspace` 的真实文件（没改任何东西）。

---

## 1. 现在到底存了什么、多大

每集一个文件夹，都是整文件 JSON：

| 文件 | 内容 | EP001_AI 实测 |
|---|---|---|
| `episodes/<集>/state.json` | 剪辑段落（647 处改动）、渲染配方、撤销历史、待批建议 | **430 KB** |
| `episodes/<集>/transcript.json` | 逐字稿 | 960 KB（导入后不再改） |
| `publish.json` / `poster.json` / `music.json` | 发布包、封面 SVG、配乐 | 36 KB / 30 KB / 1 KB |
| `imports/<集>/` | 导入中间产物（ASR、特征、AI 窗口） | 6.9 MB（只在导入时写） |
| `learning/rules.json` + `learning/decisions/<集>.json` | 学到的规则、每集的决定记录 | 6 KB + 每集 130–270 KB |
| `library/library.json`、`names.json` | 素材库索引、词表 | 5 KB 各 |

对比：整个工作区 4.5 GB，几乎全是音频（原始分轨、导出 WAV）。**每集的「数据」只有 1–2 MB（不算导入中间产物）**，100 集也就 100–200 MB。这个量级 JSON 完全没压力。

写入方式（`lacuna_app/store.py`）：先写临时文件 → fsync 落盘 → 旧文件改名成 `.bak` → 原子替换。读的时候主文件坏了自动读 `.bak`。每次点「保留/恢复/撤销」都整份重写 state.json，实测 **约 16 ms 一次**，用户无感。

## 2. 真实的损坏场景，逐个看

| 场景 | 现在会怎样 | 风险 |
|---|---|---|
| 断电 / 蓝屏 / App 崩溃写到一半 | 原子替换 + fsync：要么旧版要么新版，不会出现半截文件；最坏丢最后一次点击 | 低 |
| 两个进程同时写 | 只有一个 App 进程在写（端口 8765 被占时第二个起不来）；进程内每集有锁 | 低 |
| 进程内两个后台任务同时改 `names.json` / `rules.json` | 这两处读-改-写没加锁，极小概率丢一次修改（不会坏文件） | 很低 |
| **程序 bug 写进了「格式正确但内容错」的数据** | 只有一代 `.bak`，再点两下就把好的版本覆盖了；没有历史快照 | **中** |
| **硬盘坏 / 误删工作区** | 工作区没有任何备份。音频 Riverside 上还有原件，但剪辑决定、学到的规则、发布包、封面全没了 | **中（后果最重）** |
| 更新后回滚 | 现在所有格式都是 schema 1，没问题。将来某次更新升级了格式，回滚到旧版会打不开那些集（"unsupported state schema"） | 现在无，将来中 |
| 同步盘（OneDrive/iCloud）| 工作区在 `C:\Projects`，不在同步盘里，现在没事。放进同步盘两边同时改会出冲突副本 | 现在无 |

结论：**「文件写坏」这件事已经防住了；没防住的是「好数据被覆盖」和「整盘丢失」**。换数据库解决不了这两个，备份才能解决。

## 3. 按几十上百集估算

我把 EP001_AI 复制成 30 集在本地实测：每集打开 ≈ 0.09 秒、常驻内存 ≈ 5.5 MB。问题在于首页和「学到的规则」页会**把所有剧集完整读进内存并且一直不释放**（`server.py` 的 `open_episodes`）：

| 集数 | 首页首次打开 | 常驻内存 |
|---|---|---|
| 30 | ~3 秒 | ~170 MB |
| 100 | ~9 秒 | ~550 MB |
| 200 | ~18 秒 | ~1.1 GB |

另外每集一旦试听过，会再留一份最多 192 MB 的音频缓存，也不释放。16 GB 内存的机器上，一次会话里听过十几集就会明显吃内存。

这是「读取方式」的问题，不是 JSON 的问题，换数据库也得同样改。修法：首页只读一个小的摘要索引；剧集按最近使用保留几个，其余释放。

单集体积不是问题：2 小时、上千处改动的一集 state.json 估计 1 MB 以内，保存仍在几十毫秒。撤销历史会随操作增长，但 EP001 里只有 9 KB，可以以后再设上限。

## 4. 什么时候该换数据库（SQLite）

SQLite 是单个本地文件的数据库，仍然完全本地，不违反「音频不出机器」。值得换的信号：

1. **学习要跨上百集查询**：比如「Pei 的嗯在所有集里被保留的比例」。现在每次打开「学到的规则」都要把所有集的决定文件全读一遍（每集 130–270 KB，100 集约 27 MB）。
2. **要做跨集搜索**：搜某个片名在哪几集里提到过。
3. **真的两个人同时编辑同一集**（但见下节，这种情况 SQLite 也不是答案）。

预计你做到 100 集左右、或者学习功能升级时会碰到第 1 条。当初的决定就是存储层保持可替换，所有读写都经过 `store.py` 的两个函数，换的时候改动集中。

## 5. 和 Pei 共享：各方案的差别

| 方案 | 怎么做 | 优点 | 问题 |
|---|---|---|---|
| A. 各自工作区 + 打包交换（推荐） | 一集剪完/交接时导出「剧集包」（JSON + 她已有的音频按 sha256 自动对上），对方导入 | 最简单，永不冲突，和 JSON / SQLite 都兼容 | 不能同时改同一集；需要明确谁在剪 |
| B. 工作区放共享同步盘 | OneDrive / iCloud 共享文件夹 | 看起来省事 | JSON 会出冲突副本、后写覆盖先写；**SQLite 放同步盘更糟，可能直接把库同步坏**。音频几 GB 同步也慢。至少要加「谁在编辑」的锁文件 |
| C. 云端数据库 / 服务器 | 文本数据放云端，音频各自本地 | 真正实时协作 | 违背 local-first，要账号、要服务器，工作量大；你们俩的使用方式用不上 |

另外一个和共享有关的现有问题：state.json 里记的是**原始音频的绝对路径**（`C:\Projects\LACUNA_Workspace\episodes\EP001_样本集\raw\Leon.wav`），到 Pei 的 Mac 上路径不存在。好在每个音频都有 sha256 指纹，可以按指纹重新找到文件。做方案 A 的时候顺手改成相对路径 + 按指纹找回。

**所以，和 Pei 共享不是换数据库的理由**；按 A 做，跟存储用 JSON 还是 SQLite 无关。

## 6. 建议与 Leon 的决定

**Leon 2026-10-17 17:24Z 决定：自动备份先不做；首页改成只缓存最近 3 集，其余用到时再加载。** 已实现（分支 `claude/storage-analysis-f5vzu3`）：100 集时首页 0.035 秒、点进一集没缓存的 0.12 秒、内存只留 3 集。第一次打开首页会建一次索引（100 集约 6 秒，以后不再需要）。

原建议：

**建议马上做（下一批）：**

1. **自动备份**：App 每天第一次启动、以及每次更新前，把工作区里所有 JSON（不含音频和导入中间产物，每集约 1–2 MB）打包到 `LACUNA_Workspace\backups\日期.zip`，保留最近 14 天 + 每次更新前的那份；设置页可以选再复制一份到 OneDrive 文件夹（只有文本和数字，没有音频）。再加一个「从备份恢复某一集」。
   约 1–1.5 小时 Claude 执行时间（含测试）。
2. **首页不再全量加载**：每集保存时顺带写一个小摘要，首页只读摘要；剧集和试听缓存只保留最近用的几集。约 1–2 小时。

**以后再做：**

6. 换 SQLite：出现第 4 节的信号时做。存储层替换 + 迁移旧数据 + 测试，约 3–5 小时。
